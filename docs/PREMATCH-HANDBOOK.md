# Прематч: как это было сделано на тестовой записи

Документ для Claude Code. Описывает рабочий способ, которым 16–19 ноября 2026 была записана и разобрана
прематч-линия Betano и Pinnacle из фида bettingco.pro: чтение событий, сопоставление матчей, рынков и исходов,
расчёт вилок и сигналов, цена закрытия, результаты матчей, статистика. Всё ниже проверено на 71 часе записи
(1 223 сопоставленных матча, 474 сыгранных, результат найден для 183).

Читать вместе с `engine/model.py`, `engine/markets.py`, `engine/signals.py` и `docs/FEED.md`. Там, где этот
документ расходится с более ранними файлами, верен он.

Ключи API в документе не приводятся. Они лежат только в `.env`.

---

## 1. Общая схема

```
фид (2 конторы) -> состояние рынков по каждой игре -> пары матчей Pinnacle/Betano
   -> каждые 2 минуты пересчёт "грязных" пар:
        лесенка Pinnacle -> ожидаемые голы -> справедливые цены
        каждая цена Betano -> перевес модели, противоположная цена Pinnacle, размер вилки
   -> журнал сигналов и журнал вилок (первое появление, сколько раз повторилось)
   -> на старте матча состояние замораживается = цена закрытия
   -> после матча: счёт и счёт первого тайма -> расчёт ставок -> отчёт
```

Движок ничего не ставит и не работает со счетами. Он только измеряет.

## 2. Чтение фида

### 2.1. Запросы

База: `https://apiparsers.bettingco.pro/GameData/`. Заголовок `X-Api-Key`.

| Запрос | Что отдаёт | Ограничение |
|---|---|---|
| `GetBookmakerData?bookmakerType=Pinnacle` (или `Betano`) | Полное состояние плюс накопленные изменения | 1 раз в 5 секунд, ответ 30–100 МБ |
| `GetBookmakerSnapshots?bookmakerType=…&lastSnapshotTime=…&sessionId=…` | Изменения после указанного времени | не чаще 500 мс |

Прематч или лайв определяется ключом, а не параметром.

### 2.2. Форма ответа

Оба запроса возвращают объект с тремя полями (в ответе на Snapshots первые два могут быть пустыми):

```
gamesOriginModel:   { writeTime, model: { <textId игры>: Game } }
marketsOriginModel: { writeTime, model: { <textId рынка>: Market } }
snapshots: [ { sessionGuid, writeTime,
               gamesAdded[], gamesUpdated[], gamesRemoved[],
               marketsAdded[], marketsUpdated[], marketsRemoved[] } ]
```

Game: `textId, leagueName, team1NameEn, team2NameEn, startTimeStamp (сек), statusType, currentScore,
compareEventId, link, sportType, bookmakerType`.

Market: `textId, gameTextId, surebetType, marketType, subMarketType, specialKind, marketMeta,
marketParameter, marketValue, meta, eventId`.

Элементы изменений:

- `marketsAdded`: `{ textId, gameTextId, marketModel: Market }`
- `marketsUpdated`: `{ textId, value, gameTextId }` — только новая цена
- `marketsRemoved`: `{ textId, gameTextId }`
- игры аналогично, модель игры лежит во вложенном объекте.

Идентификатор рынка и игры это `textId`. Он стабилен между сессиями, поэтому состояние удобно держать в словарях
по `textId`.

### 2.3. Порядок работы клиента

1. `GetBookmakerData` -> построить состояние из `gamesOriginModel` и `marketsOriginModel`.
2. Применить по порядку все `snapshots` из того же ответа: они новее базовой модели.
3. Запомнить `sessionGuid` и `writeTime` последнего снимка.
4. Дальше в цикле `GetBookmakerSnapshots` с этими двумя значениями, применять изменения, обновлять `writeTime`.

Рабочий ритм на тесте: конторы опрашиваются по очереди, пауза 5 секунд между запросами, то есть каждая контора
раз в 10–12 секунд. Этого достаточно: Betano отстаёт от Pinnacle на минуты.

Брать только футбол: `textId` игры содержит `/Football/`. Рынок без известной футбольной игры пропускать.

### 2.4. Коды ответов

| Код | Смысл | Действие |
|---|---|---|
| 200 | изменения | применить |
| 204 | изменений нет | ничего |
| 400 `SessionId mismatch` | сессия поставщика сменилась | полная перезагрузка через `GetBookmakerData` |
| 401 `API key has expired` | ключ истёк | остановиться, сообщить |
| 429 | один ключ опрашивают два клиента | оставить одного клиента |

Если в снимке `sessionGuid` отличается от запомненного, тоже делать полную перезагрузку.

### 2.5. Перезагрузка сессии: главная ловушка

Pinnacle в фиде перезапускается примерно каждые 40 минут. Betano реже. При перезапуске все рынки как бы
удаляются и через секунды появляются заново.

Правило: перезагрузка это не событие рынка. Нельзя превращать её в «рынок удалён, рынок добавлен, цена изменилась».
Иначе за три дня получается 675 тысяч ложных событий и ломается подсчёт движений цены.

Как сделано:

- перед применением новой базы для каждой игры этой конторы, которая ещё не началась, отложить старый словарь цен
  и завести пустой;
- применить базу и её снимки;
- рынка нет в новой базе -> он снят;
- цена та же -> ничего не произошло;
- пометить пару «грязной» для пересчёта.

### 2.6. Заморозка на старте

Любое изменение со временем `t >= startTimeStamp` игры игнорируется. Состояние, которое осталось, и есть цена
закрытия прематча. Для Betano дополнительно хранить последнюю ненулевую цену по каждому исходу: рынок могут снять
за минуты до старта.

Удаление игры из фида состояние не стирает.

### 2.7. Пропуски записи

Если по конторе не было данных больше 10 минут, это пропуск. Матчи, стартовавшие внутри пропуска, считать без
цены закрытия. На тесте пропуски были из-за остановки программы-клиента, по часу-полтора.

### 2.8. Особенности, замеченные на данных

- У Betano `compareEventId = 0`. Матчи сопоставляются по названиям и времени (раздел 3).
- У Pinnacle `compareEventId` это id матча, он же стоит в начале `meta` каждого голевого рынка.
- Цены Betano «мигают»: около 30% изменений возвращаются к прежнему значению. См. раздел 8.
- Счёт в фиде ненадёжен, минуты матча нет. Результаты брать снаружи (раздел 10).
- Цены Pinnacle приходят как float32 (2.5899999141693115). Сравнивать с допуском не нужно, но округлять при
  выводе.
- Объём фида меняется от ключа к ключу. На тестовом ключе у Betano было около 790 футбольных матчей и 22 тысячи
  рынков, на новом 1 415 матчей и 119 тысяч рынков. Классификатор Betano на новом объёме надо перепроверить
  (раздел 4.4).

## 3. Сопоставление матчей Pinnacle и Betano

Общего идентификатора нет. Работало так.

### 3.1. Разбор названия

Для каждой команды из названия и названия лиги получить:

- `age`: число из шаблона `u-?(\d\d)` в названии команды или лиги (U19, U21, U23), иначе 0;
- `women`: признак по `(w)`, `women`, `femenin`, `feminin`, `frauen`, `ladies`, `damen`, `(f)`;
- `reserve`: есть токен `ii`, `b`, `2`, `res`, `reserves`;
- `tokens`: название в нижнем регистре, без диакритики, только буквы и цифры, без служебных слов.

Служебные слова: `fc cf sc ac afc cd ca club de the fk sk if bk cs sv as us ss rc ud sd fs cfc sfc ff kf nk sp bc c f
team and`. Возрастные метки, `w` и метки резерва в токены не входят.

Возраст брать в том числе из лиги: у Pinnacle команда пишется «Czechia», а лига «U21 Euro Championship Qualifiers».

### 3.2. Сходство

```
sim(A, B) = (число токенов A, для которых в B есть равный токен
             или один является началом другого при длине от 4) / min(|A|, |B|)
```

### 3.3. Условия пары

- старт отличается не больше чем на 15 минут;
- `age`, `women`, `reserve` совпадают у обеих команд;
- `sim` по хозяевам >= 0.5, по гостям >= 0.5, сумма >= 1.5;
- порядок команд одинаковый (хозяева с хозяевами);
- если кандидатов несколько, брать с наибольшей суммой;
- одна игра входит только в одну пару.

Сопоставление идёт на лету: новая игра сравнивается с ещё не сопоставленными играми другой конторы.

### 3.4. Что ломалось

- Без проверки возраста «Ireland U21 – Finland U21» цеплялся к другому матчу U21 в то же время.
- Пара «Manchester United / Manchester City» даёт 0.5 по одной команде, поэтому нужен порог суммы 1.5.
- Женские команды: у Betano `(W)` в названии команды, у Pinnacle слово Women в лиге.

Объём на тесте: 1 223 пары за 71 час. Перед расчётом стоит выборочно проверять 20–30 пар глазами.

## 4. Сопоставление рынков и исходов

### 4.1. Единый ключ исхода

Каждый рынок обеих контор приводится к виду `(период, семейство, линия, сторона)`. Строковый ключ:
`период|семейство|линия|сторона`, например `FT|tot|2.5|o`, `2H|x|0|a`, `1H|dc|0|x2`.

| Поле | Значения |
|---|---|
| период | `FT` матч, `1H` первый тайм, `2H` второй тайм (только Betano) |
| семейство | `x` исход, `dc` двойной шанс, `dnb` фора 0, `tot` тотал, `tt1` и `tt2` тоталы команд, `hc` фора (только Pinnacle), `btts` обе забьют, `odd` чёт/нечет |
| сторона | `h a d`; `1x x2 12`; `o u`; `y n`; `o e` |

Период: `marketType 0` -> `FT`; `marketType 3` и `marketMeta '1'` -> `1H`; `marketType 3` и `marketMeta '2'` -> `2H`
(только для Betano). Всё остальное отбрасывается.

Коды `surebetType`: 0 П1, 1 П2, 2 Х, 3 1Х, 4 Х2, 5 12, 6/7 ИТ1 больше/меньше, 8/9 ИТ2 больше/меньше,
10/11 тотал больше/меньше, 12/13 нечет/чёт, 15/16 фора 1/2, 17/18 да/нет.

Готовый код: `engine/markets.py`, функции `classify_pinnacle` и `classify_betano`. Они проверены на записи.

### 4.2. Pinnacle

- Брать только `subMarketType == 0` и `specialKind == 0`.
- `meta` обязан начинаться с `<compareEventId>|`. Это отсекает угловые и карточки: они висят на той же игре, но у
  них другой id в начале `meta`. Без этой проверки в лесенку тоталов попадают тоталы угловых, и подбор ожидаемых
  голов уезжает (ошибка 3.7% вместо 1.0%).
- Фора: линия всегда в терминах хозяев. Для `surebetType 16` (фора гостей) линия берётся с обратным знаком.
- Исход `x` только при пустом `marketParameter`.

### 4.3. Betano

- `subMarketType == 0`.
- Отбросить по `meta` всё, что не про голы: `corner|card|booking|offside|shot|foul|penalt|throw|goal kick|player|
  scorer|minute|next|race|interval`.
- Для периода `FT` отбросить рынки, где в `meta` есть `Half|Second|2nd|1st`: это рынки таймов с неправильным типом.
- `specialKind 200` с типами 0/1 это фора 0 (`dnb`).
- Исход `x` только если в `meta` есть `Result`. Двойной шанс только если есть `Double Chance`. Тоталы только если
  есть `Goals`. Обе забьют по шаблону `^Both Teams to Score( in (First|Second) Half)? \|`. Чёт/нечет только для
  матча и только `Total Goals Odd/Even`.
- В тестовом фиде у Betano не было фор и комбинированных рынков.

### 4.4. Дубли

У Betano бывает несколько рынков, которые дают один и тот же ключ (обычный и «азиатский» тотал с той же линией).
Правило: ключ принадлежит первому рынку, который его занял в текущей сессии. Остальные игнорируются, пока
владелец не снят. Без этого цена по ключу скачет между двумя рынками и выглядит как движение.

На расширенном фиде (119 тысяч рынков) это правило и фильтры из 4.3 нужно перепроверить: выгрузить по 20 примеров
`meta` на каждое семейство и убедиться, что туда не попало лишнее.

### 4.5. Четвертные линии

Линии 0.25 и 0.75 рассчитываются как две половинные ставки на соседние линии. Это учтено и в модели
(`win_loss`), и в расчёте результата (раздел 11).

## 5. Модель справедливых цен

Код: `engine/model.py`. Кратко, что он делает.

1. Из цен Pinnacle по паре собирается лесенка для `FT` и для `1H`:
   `{x: {0: П1, 1: П2, 2: Х}, tot: {линия: {o, u}}, hc: {линия: {h, a}}, tt1: {...}, tt2: {...}}`.
   В подборе участвуют `x`, `tot`, `hc`. Тоталы команд в подбор не входят, они нужны для проверки и для вилок.
2. Маржа снимается пропорционально внутри каждого рынка. Рынки с вероятностью стороны вне 12–88% пропускаются.
3. Подбираются ожидаемые голы хозяев и гостей (Гаусс–Ньютон, 10 шагов, невязки в логитах).
4. Таблица счетов 11×11: Пуассон с поправкой Диксона–Коулза и разбросом общего темпа.
   Параметры: матч `rho = -0.05, v = 0.15`; таймы `rho = 0, v = 0.15`.
5. Второй тайм: ожидание матча минус ожидание первого тайма, таймы считаются независимыми.
6. Подбор отбрасывается, если среднеквадратичная невязка больше 0.12.

Проверка на 7 135 ценах закрытия в 130 матчах с результатом: число побед совпало с расчётным на каждом семействе
и каждом периоде в пределах 0–1.6%. Модель в среднем точна. Расхождение с прямой ценой Pinnacle по тому же
исходу: в среднем 0.2%, разброс 1.5% (у исходов матча до 5%).

## 6. Цикл оценки

- Пара помечается «грязной» при любом изменении цены в любой из двух игр.
- Сетка 2 минуты. На каждом шаге пересчитываются только грязные пары. Сетка 20 минут теряла больше 80% сигналов.
- Оценка идёт, пока до старта остаётся время. Сигналы и вилки записываются, только если до старта не меньше
  15 минут. Позже этого модель всё равно пересчитывается: последний удачный расчёт нужен как «справедливая цена
  на закрытии».
- Для каждой цены Betano по паре:
  - `ev = w * (k - 1) - l`, где `w` и `l` доли выигрыша и проигрыша из модели, `k` цена Betano;
  - `opp` = лучшая противоположная цена Pinnacle (раздел 7);
  - `arb = 1 / (1/k + 1/opp) - 1`, если `opp` есть.
- В журнал сигналов пишется первое появление исхода с `ev >= 0.055`. При повторе увеличивается счётчик и
  максимум.
- В журнал вилок пишется первое появление исхода с `arb > 0`, независимо от `ev`. Это отдельный журнал.

Поля записи: пара, ключ, время, цена Betano, `ev`, `w`, `l`, `opp`, `arb`, минут до старта, число повторов,
максимум.

`PRICE_MUST_HOLD_SEC` из `engine/signals.py` на тесте не применялся. Вместо него работал фильтр мигающих матчей
(раздел 8).

## 7. Как образуется вилка

Вилка считается на уровне одного исхода Betano против противоположной ставки в Pinnacle.

### 7.1. Противоположная цена

| Исход Betano | Противоположная ставка в Pinnacle |
|---|---|
| `x`, гости | лучшее из: фора хозяев +0.5; синтетика «П1 или Х» |
| `x`, хозяева | лучшее из: фора гостей +0.5 (линия −0.5 в терминах хозяев); синтетика «П2 или Х» |
| `x`, ничья | синтетика «П1 или П2» |
| `dnb`, хозяева / гости | другая сторона форы 0 |
| `dc 1x` | П2 |
| `dc x2` | П1 |
| `dc 12` | Х |
| `tot`, `tt1`, `tt2` | другая сторона той же линии |
| `btts`, `odd` | нет рынка в Pinnacle |
| любой исход `2H` | нет рынка в Pinnacle |

Синтетика из двух исходов: `1 / (1/a + 1/b)`. Это цена ставки, покрывающей оба исхода.

Код: `opposite_price` в `engine/signals.py`.

### 7.2. Размер вилки и полосы

`arb = 1 / (1/k_betano + 1/opp) - 1`.

| Значение | Полоса | Смысл |
|---|---|---|
| `arb > 0` | вилка | сканер её покажет |
| `-1.5% < arb <= 0` | рядом | вилка почти сходится |
| `arb <= -1.5%` | далеко | рынок есть, вилки нет |
| `opp` отсутствует | нет рынка | ни вилка, ни классический валуй невозможны |

Модель 1 = сигнал модели и `arb <= 0` или рынка нет. Модель 2 = сигнал модели и рынка нет. Запас от вилки
(0, −1.5%, −3%) не зашивать в код, а резать при анализе по полю `arb`.

Вилка на исходе и вилка на рынке это разное. Если вилка есть на «тотал больше 2.5», исход «обе забьют» в том же
матче от этого вилочным не становится.

### 7.3. Что показала запись

- Вилок с Betano много: 495 исходов в 183 матчах за 71 час, около 167 в сутки. Типичный размер 1.1%, средний 2.0%.
- Betano отстаёт от Pinnacle на 4–7 минут. Из 359 вилок первых 39 часов 341 открылась движением Pinnacle.
- После появления вилки или сигнала Betano снижает цену примерно в 9 случаях из 10, в среднем на 12–14%.

## 8. Фильтр мигающих матчей

По каждой игре Betano считать: число изменений цены и число «возвратов» (новая цена равна той, что была перед
текущей). Матч исключается, если изменений не меньше 40 и доля возвратов больше 45%. На тесте это 48 пар из 1 223.

Причина миганий не выяснена. Вопрос к поставщику фида: существовали ли такие цены на сайте.

## 9. Цена закрытия

Для каждой записи журнала после старта матча:

- `kC`: последняя цена Betano по этому исходу до старта;
- справедливая цена на закрытии: последний удачный расчёт модели, если он не старше 30 минут до старта;
- `evC`: перевес цены сигнала относительно справедливой цены на закрытии;
- снижение: `kC / цена сигнала - 1`.

Важно: перевес по цене закрытия оказался слабым критерием. По моделям 1 и 2 он был +5.5% и +8.8%, а фактический
результат −10% и 0%. Использовать его как раннюю проверку, но выводы делать по факту.

## 10. Результаты матчей

Нужны счёт матча и счёт первого тайма. В фиде их брать нельзя.

| Источник | Что даёт | Как читать |
|---|---|---|
| `flashscore.mobi/?d=-N` | список матчей за день, N от 0 до 7 | обычный HTML, блок `#score-data`: `<h4>` лига, `<span>` время, текст «A - B», ссылка класса `fin` со счётом |
| `flashscore.mobi/match/<id>/` | счёт по таймам | в тексте `2-0 (1-0,1-0)` |
| `footballwebpages.co.uk/<команда>/fixtures-results` | английские низшие лиги | строка таблицы: `Tue 17 Nov H Wroxham Isthmian North (1)1 - 2(0)`, в скобках счёт первого тайма |
| ESPN `site.api.espn.com/apis/site/v2/sports/soccer/all/scoreboard?dates=YYYYMMDD&limit=1000` | только крупные турниры | JSON; первый тайм считать по голам с минутой до 45 |

Покрытие на тесте: ESPN дал четверть наших матчей, Flashscore поднял до 88%. Основной источник Flashscore.

Правила чтения Flashscore:

- время на странице центральноевропейское (UTC+1 зимой);
- `2-2aet` значит дополнительное время: счёт основного времени это сумма первых двух частей в скобках
  (`0-0,2-1,0-1` -> 2:1, первый тайм 0:0);
- `1-1 (Pen: 5-3)` значит серия пенальти: счёт основного времени 1:1;
- `-` вместо счёта: матч не состоялся, ставки не считаются;
- лёгкая версия показывает не все турниры. Не нашлись: третья лига Мексики, низшие лиги Египта и Замбии,
  региональная Испания, часть женских и юношеских лиг.

Ограничения: SofaScore закрыт проверкой «вы человек», её не обходить. ESPN при запросе всех лиг подряд закрыл
доступ, запрашивать только общий список за день. Между запросами страниц держать паузу около полсекунды.

Сопоставление результата с парой: старт в пределах 30–60 минут, те же возраст и женский признак, сходство
названий по правилам раздела 3 (у Flashscore названия короче: «Sheffield Wed U21», «Arab Contractors» вместо
«Al-Mokawloon Al-Arab»). Спорные случаи выводить списком на ручную проверку.

Сверка: 26 матчей, найденных и в ESPN, и на Flashscore, совпали полностью.

## 11. Расчёт ставки

Счёт для периода: `FT` счёт матча; `1H` счёт первого тайма; `2H` разница между ними. Если счёта первого тайма нет,
ставки на таймы не рассчитываются.

| Семейство | Выигрыш | Возврат |
|---|---|---|
| `x` | исход совпал | нет |
| `dc` | один из двух исходов | нет |
| `dnb` | победа выбранной команды | ничья |
| `tot`, `tt1`, `tt2` | сумма больше или меньше линии | сумма равна линии |
| `btts` | обе забили (или нет) | нет |
| `odd` | чётность суммы | нет |

Четвертная линия: среднее двух половинных ставок на `линия − 0.25` и `линия + 0.25`.
Результат в единицах ставки: выигрыш `k − 1`, проигрыш `−1`, возврат `0`.

## 12. Статистика

- Ставки внутри одного матча зависимы. Десять сигналов на разные тоталы одного матча это по сути одна ставка.
  Погрешность считать по матчам: сумма результата по каждому матчу, затем
  `SE = sqrt(дисперсия сумм по матчам * число матчей) / число ставок`.
- Всегда показывать второй срез: один сигнал на матч (с наибольшим перевесом или наибольшей вилкой).
- Рядом с числом побед показывать ожидаемое по модели: сумма `w` по рассчитанным ставкам.
- Сигналы с ценой Betano от 5 исключать: маржа Betano там 30–60%, модель завышает вероятность.
- Базовый уровень: случайная цена Betano даёт −11% к справедливой.

Маржа Betano на закрытии по сумме вероятностей: исходы 10–12%, фора 0 9–11%, тоталы 8–10%, обе забьют 7–9%,
тоталы команд 7%, двойной шанс 6%. Отставание цены от справедливой по коэффициентам: до 1.5 −4%; 1.5–2 −7%;
2–3 −10%; 3–5 −17%; 5–10 −32%; выше 10 −58%.

## 13. Что получилось на тесте

71 час, цена до 5.

| | Модель 1 | Модель 2 | Одно плечо вилки |
|---|---|---|---|
| Сигналов | 430 в 178 матчах | 214 в 86 матчах | 495 в 183 матчах |
| Перевес к закрытию | +5.5% | +8.8% | +6.5% |
| Рассчитано ставок | 223 в 90 матчах | 103 в 42 матчах | 265 в 90 матчах |
| Выиграло / ожидалось | 85 / 99 | 47 / 50 | 136 / 137 |
| Итог, ставок | −21.4 | +0.2 | +11.9 |
| ROI | −10% ±12% | 0% ±20% | +4.5% ±8% |

Наблюдения:

1. Модель в среднем точна, но на отобранных сигналах завышает перевес. Отбор вытаскивает случаи, где оценка
   ошиблась в нашу пользу. Реальный перевес моделей 1 и 2 оценивается в 0–3% вместо расчётных 6–8%.
2. Расчётный перевес модели не предсказывал результат. Размер вилки предсказывал только в верхнем хвосте: вилки
   от 4% дали +12.7 ставки на 27 ставках, все остальные вместе около нуля.
3. Плюс одного плеча вилки пришёл с исходов (+13.1 на 185 ставках) и цен до 2.0 (+12.5 на 169). Тоталы и тоталы
   команд не дали плюса ни в одной схеме.
4. Факт совпал с расчётом на исходах таймов (85 ставок, 36 побед при ожидании 36) и на фаворитах (35 ставок,
   27 при ожидании 23). Выборки малы.
5. Ни одна из итоговых цифр статистически не отличается от нуля. Чтобы отличить +3% от нуля по модели 1, нужно
   400–500 матчей с результатом, это 7–10 дней записи.

Ошибки анализа, которые не надо повторять:

- вывод по 6 закрытиям («модель 2 не работает в тихих матчах») оказался неверным;
- вывод «тоталы команд это брак данных» оказался неверным: цены были настоящими, ставки просто проиграли;
- ROI по четверти матчей (только ESPN) был −49%, на полной выборке −10…−18%. Неполное покрытие результатов
  искажает картину сильнее, чем кажется.

## 14. Что должен делать движок

Обязательное:

1. Клиент фида по разделу 2, с правильной обработкой перезагрузки сессии и заморозкой на старте.
2. Сопоставление матчей по разделу 3 с выгрузкой спорных пар.
3. Классификация рынков по разделу 4 с правилом владельца ключа.
4. Цикл оценки по разделу 6: два журнала, сигналы и вилки.
5. Цена закрытия по разделу 9.
6. Результаты по разделу 10, расчёт по разделу 11.
7. Отчёт по разделу 12: по матчам, один сигнал на матч, выиграло против ожидалось.

Поля журнала сверх базовых: полоса вилки, период, семейство, сторона, цена, минут до старта, признак «лучший в
матче», цена закрытия, перевес на закрытии, результат, источник результата.

Срезы, которые нужны в каждом отчёте: модель 1, модель 2, одно плечо вилки; исходы отдельно от тоталов; периоды;
цена до 2, 2–3, 3–5; размер вилки 0–1, 1–2, 2–4, от 4%; фаворит и аутсайдер.

Один ключ опрашивает одна программа. Вторая вызывает ошибки 429 у обеих.

## 15. Проверки для тестов

- Перезагрузка сессии с теми же ценами не порождает ни одного изменения цены и ни одной «грязной» пары сверх
  самой перезагрузки.
- Рынок угловых Pinnacle не проходит классификатор.
- Два рынка Betano с одним ключом: цена по ключу не меняется, пока жив первый.
- Фора гостей Pinnacle −0.5 попадает в ключ `hc|0.5|a`.
- `x` гости против Pinnacle: противоположная цена это максимум из форы хозяев +0.5 и синтетики П1/Х.
- Изменение цены после `startTimeStamp` не меняет состояние.
- Тотал 2.25 больше при счёте 1:1: половина ставки проиграна, половина возвращена.
- Фора 0 при ничьей: возврат.
- `2-2aet` с частями `0-0,2-1,0-1` даёт счёт 2:1 и первый тайм 0:0.
- Пара «Ireland U21 – Finland U21» не сопоставляется с матчем других сборных U21 в то же время.
