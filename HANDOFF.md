🔧 **НАЙДЕНА И ИСПРАВЛЕНА УТЕЧКА РЕАЛЬНОГО IP (релиз 0.7.40):**
- **Что показал индикатор 0.7.39:** прокси конторы ПРИМЕНЯЕТСЯ — Betano-сессия выходит через 89.117.5.123 (PT),
  Pinnacle через 181.214.155.115 (MX), оба ≠ реальный ВДС 138.201.85.223. НО Betano всё равно банил.
- **Ключевая зацепка владельца:** Betano предлагал перейти на **немецкий** Betano, а реальный IP ВДС — **немецкий**.
  Значит Betano видел РЕАЛЬНЫЙ немецкий IP, хотя сессия конторы шла через PT. Расхождение: индикатор проверяет
  `net.request` через сессию конторы (PT), а утечку давало **другое окно**.
- **Истинная причина (НЕ прокси-провайдер, а наш код):** `resolveEventViaNav` (`main.cjs`) для получения
  deep-ссылки события создавал скрытое окно с **`partition: "persist:surebet"`** (сессия surebet, БЕЗ прокси
  конторы) и шло по surebet-редиректу **физически на betano.pt реальным IP ВДС** → Betano видел немецкий IP →
  `/myaccount/ban/country-341630`. Эта ban-ссылка затем грузилась в окно конторы. Т.е. окно конторы было
  проксировано, но окно-РЕЗОЛВЕР — нет.
- **Фикс (внесён, тесты 70/70, load OK):** в `resolveEventViaNav` теперь ловим редирект/навигацию `surebet→контора`
  на `will-redirect`/`will-navigate` и **`preventDefault()` ДО захода** на сайт конторы — surebet-сессия больше не
  стучится на betano.pt реальным IP. Чистую deep-ссылку грузим уже в ОКНЕ КОНТОРЫ (с её прокси). Лог:
  `резолв: перехватил ссылку конторы на surebet-сессии, обрываю (без утечки IP)`.
- **ПРОВЕРКА ПОСЛЕ ОБНОВЛЕНИЯ на 0.7.40:** владелец на новой ВДС → «Запуск бота» на Betano-вилке → в логе
  должна быть строка «резолв: перехватил ссылку … обрываю (без утечки IP)», а deep-ссылка открыться уже
  **без** `/myaccount/ban/country`. Если бан всё равно останется — тогда уже датацентр-IP/аккаунт
  (резидентный прокси под страну Betano + чистый аккаунт).

**0.7.38 — ИСТИННАЯ причина «копеечных ставок» (важно):** Betano-кап был `min(maxStake, balB)`, а
`readBookmakerBalance("betano")` хватал сумму уже ПОСТАВЛЕННОЙ ставки («Single 1,29 €»/«CASH OUT», top~224)
и считал её балансом → `cap=min(MAX, 1.29)=1.29`. Петля: каждая поставленная ставка → «баланс» для следующей →
ставки схлопывались (2.70→2.66→2.54→1.29). Лимит-поле (0.7.37) тут ни при чём. **Фикс:** Betano-кап = ТОЛЬКО
`maxStake` (кнопка MAX уже = min(макс события, реальный баланс)); `balB` для капа НЕ используем (`balB=null`).
Pinnacle оставлен `min(max, balP)` — там баланс из шапки честный. Итог потолка: min(MAX Betano, баланс Pinnacle,
лимит панели). ⚠️ Если Betano MAX не прочитался (null) — кап Betano = ∞, ограничивают только лимит панели и
балансировка под Pinnacle; рекомендуется держать лимит в панели как страховку.

**0.7.37 — фикс «лимит вилки застрял на 5€»:** баг был в рендере — `renderStatus` на КАЖДОМ статус-тике
заполнял поле `#vilkaLimit` сохранённым значением, если поле пустое → очистка лимита тут же затиралась
старыми 5€. Фикс: поле заполняется из настроек ТОЛЬКО ОДИН раз при загрузке (`vilkaLimitInit`), дальше не
трогаем — очистка (=без лимита) и новое значение (1000) сохраняются (`onchange`→`saveSettings`) и читаются

(min(макс, баланс)); при балансе 23 USDT крупнее ~23 на плечо Pinnacle всё равно не поставить — нужен баланс.

### ЗАДАЧА: «доработай юзерагент» (если владелец так скажет — это про ЭТО)
**Сейчас:** UA берётся из фикс-пула `UA_PRESETS` (`lib/bookers.cjs:~7`) — 3 строки Chrome/Win64, версии 129/130/131,
вид `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/130.0.0.0 Safari/537.36`.
Генерация: `randomFingerprint()`/`randomUA(current)` (`lib/bookers.cjs`), кнопка «🎲 новый UA» (IPC `randomize-ua`
в `main.cjs`, рендер в `renderer/app.js` `uaRow`). Применение фингерпринта: `buildFingerprintScript(fp)`
(`lib/bookers.cjs:~68`) + `Network.setUserAgentOverride({userAgent, acceptLanguage, platform})` в `openBookerProfile`
(`main.cjs:~212`, CDP). **Client Hints НЕ подменяются** (нет `userAgentMetadata`).
**Жалоба владельца:** «меняется только Chrome/130 — это мало».
**Суть (объяснено владельцу):** в реальном UA Chrome/Win меняется ТОЛЬКО версия Chrome (остальное у всех одинаково),
а версию нельзя гнать далеко от реального движка (Electron 33 = Chromium ~130), иначе `navigator.userAgentData`
(Client Hints) рапортует 130 → рассинхрон с UA → палево. **Правильная доработка (вариант B):** генератор UA
(диапазон версий, опц. Edge `Edg/…`/Opera `OPR/…`) + СИНХРОННАЯ подмена Client Hints (`userAgentMetadata`: brands,
fullVersionList, platform) в `setUserAgentOverride` И в `buildFingerprintScript` (`navigator.userAgentData`), чтобы
UA == Client Hints == движок. Без Client Hints больше вариативности = БОЛЬШЕ палевно (не делать «просто больше UA-строк»).
Альтернатива: обновить Electron → реальный Chromium свежее → честный UA новой версии без рассинхрона.

## Что это
Windows-приложение (Electron) для вилок:
1. следит за вилками на surebet.com (через окно сайта) и шлёт сигналы с **Pinnacle** в Telegram;
2. встроенный **антидетект-браузер** контор (Betano, Pinnacle): своя сессия + прокси + отпечаток + гео на контору;
3. клик по плечу вилки → открывает нужную контору **сразу на событии**;
4. **«Запуск бота»** — авто-цикл: сам ловит вилку Betano+Pinnacle(Delayed), кликает оба плеча, выбирает
   исходы, читает макс/баланс, считает суммы калькулятором, вписывает; ставит только при тумблере БОЕВОЙ.

## Оркестратор «Запуск бота» (0.7.15–0.7.17, dry-run) — ПОДТВЕРЖДЁН вживую
**Принцип (важно): бот НЕ парсит ссылки — он КЛИКАЕТ плечи в сканере, как рукой.** Статический
`href` плеча НЕ содержит `json_body` (surebet достраивает nav-ссылку JS при клике), поэтому вилку
ищем ПО ИМЕНАМ контор в DOM (как Telegram-сигналы), а событие открываем кликом → `setWindowOpenHandler`
ловит nav-ссылку → `routeLeg` открывает событие. Токен вилки = сегмент после `/prong/N/` (общий для плеч).

Поток (`main.cjs`):
- `findVilka(skip)` — ищет в `tbody.surebet_record` пару Betano + Pinnacle **(Delayed)** по тексту имени
  конторы (`data-testid="surebet-leg-bookmaker"`, имя содержит `pinnacle`+`delayed`); возвращает токен +
  индексы плеч (prong). НЕ кликает. `skip` = токены уже пробованных.
- `clickVilkaLeg(token, prong)` — кликает ОДНО плечо. **Плечи открываем ПО ОЧЕРЕДИ** (Betano → ждём
  событие → Pinnacle → ждём событие): параллельное дохождение через surebet валило Pinnacle (0.7.16 баг).
- `selectLegOutcome` (выбор исхода + макс + баланс) обоих → `vilkaStakes` → `fillStakeOnly` обоих →
  сводка. live (клик постановки) только при тумблере БОЕВОЙ И `oddsOk!==false` обоих.
- **Режим ОЖИДАНИЯ + ПРОПУСК:** «Запуск бота» взводит (`botArmed`); цикл слежения `tick` ловит вилку.
  Не смог (рынок/событие/расчёт) → токен в `triedVilkas` (blocklist), **остаётся взведён, ищет дальше**.
  Успех → разоружается. Кнопка-тумблер: «⏹ Стоп (жду вилку)». IPC `run-bot` (arm/disarm, чистит blocklist).
  В панель push-ом: `skipped`→«⏭ пропустил…, ищу дальше», `ok`→сводка. Доходность НЕ фильтруем (любая).
- `placeBet` (IPC dry-run/place одного плеча) = `selectLegOutcome`+`fillStakeOnly`+`clickPlace`.
- **Не перезагружаем surebet, пока `botBusy`** (перезагрузка рвала дохождение через surebet-сессию).

Чтение **макса**: `readBookmakerMax` — Pinnacle текст «Max bet USDT …», Betano кнопка `.max-button`→поле.
Чтение **баланса**: `readBookmakerBalance` (эвристика: листовой элемент шапки с валютой+числом, исключаем
max/bet, берём верхний; логирует кандидатов). Потолок плеча = `min(макс, баланс, лимит панели)`. `parseMoney` (US/EU).
Панель: поле «Лимит вилки на плечо €» (`vilkaLimitEur`), курс USD→EUR, кнопка, сводка `botResult` (с балансами).

## Ключевые технические нюансы (грабли, на которых уже наступили)
- **CDP-отпечаток зависает**, если слать команды до готовности рендерера → сначала `loadURL("about:blank")`, потом CDP, потом сайт (иначе loadURL не вызывается = белый экран).
- **Авторизация HTTP/HTTPS-прокси** — событие `login` ловить на **`win.webContents.on("login")`**, НЕ на session (иначе 407 → ERR_TUNNEL_CONNECTION_FAILED −111).
- **Авторизованный SOCKS5** Chromium не умеет → локальный мост (`lib/proxyBridge.cjs`), сессия указывает на `http://127.0.0.1:<port>`.
- **Закрытие окна конторы** роняло процесс → на `win.on("close")` отцеплять `webContents.debugger.detach()`.
- **React-инпуты** (купоны): вписывать через нативный setter + `_valueTracker.setValue(old)` + dispatch input/change, и читать результат после паузы (~800мс).
- **Pinnacle SPA** рендерится ~10с — окно сперва пустое, это не баг.
- **«Логин surebet при клике по плечу Pinnacle» — НАСТОЯЩАЯ причина (0.7.2, доказано логом):** surebet шлёт плечо Pinnacle под брендом **`ps3838`** (а не `pinnaclesports`). Раньше таблица `BK_TO_BOOKER` его не знала → `booker=null` → срабатывал запасной путь `bookerForUrl(url)`, а в surebet-nav URL лежат **оба** плеча → совпадало слово «betano» → ссылка `su.surebet.com/...` грузилась в **окно Betano** (там нет surebet-сессии) → **логин surebet**. Фиксы: (1) `bkToBookerId(bk)` — сопоставление по ПОДСТРОКЕ (`pinnacle|ps3838`→pinnacle, `betano`→betano), а не по точному ключу; (2) для surebet-nav с нераспознанным bk **НЕ падать в `bookerForUrl`** (return deny), иначе misroute по слову в URL. Регресс-тест в `test/bookers.test.cjs`.
- **`resolveEventViaNav` (surebet-проход) — ТОЛЬКО когда у конторы нет глубокой ссылки** (Betano = только домен). Для Pinnacle глубокая ссылка уже в `markers.link` → проход пропускается (`new URL(initial).pathname` длиннее «/»). Проход идёт в **скрытом** окне на surebet-сессии — сам по себе логин surebet пользователю НЕ показывает (мой диагноз в 0.7.1 был ошибочным — настоящая причина была в bk-мэппинге выше).
- **Отчёт о версии**: первая строка `main.log` старая; смотреть последнюю `=== старт ... ===`.

## Разметка купонов (фаза 5)
- **Pinnacle:** сумма `input[name="stake"]`; кнопка содержит «CONFIRM» + «SINGLE BET» (счётчик N = индикатор регистрации суммы); исход — кнопка `[id="eventId|период|тип|сторона|x|линия"]`, выбранный класс `selected`. Из вилки id берём из `markers.pinnacleBrExternalId`.
- **Betano:** сумма `input[id^="stakeInput"]`; кнопка «BET NOW»; исходы — `.selections__selection` (текст «Team/Over/Under <линия> <кэф>», без id).
- **surebet-nav** (ссылка плеча): `https://su.surebet.com/nav/surebet/prong/{N}/.../if?json_body={...}`. `prong/N` = индекс плеча. `json_body.prongs[N]` (строка→JSON) даёт `bk`, `markers.link` (глубокая ссылка), `markers.pinnacleBrExternalId`, `value` (кэф), `tr_terse` (тип ставки). Betano глубокой ссылки в данных не отдаёт → дохождение через `resolveEventViaNav` (скрытое окно на surebet-сессии ловит финальный URL конторы).
- **`markers.link` Pinnacle непостоянен:** иногда полное событие (`…/1631805342`), иногда общий раздел (`/en/compact/sports`) или домен. Поэтому «это событие?» определяем по **числовому id в пути** (`isEventUrl`), а НЕ по «путь длиннее /». Если не событие → проход через `resolveEventViaNav` (как у Betano) находит реальную ссылку. (Старая наивная проверка открывала общий раздел вместо матча.)
- **Бренд `ps3838` (Pinnacle) присылает минимальные markers** — НЕТ `markers.link` и НЕТ `pinnacleBrExternalId` (только событие через redirect + `tr_terse` + кэф). Поэтому выбор исхода по id невозможен → выбираем по описанию+кэфу (`pickPinnacleOutcome`). Кнопки исходов на странице: `<button>` с `id="eventId|период|тип|сторона|x|линия"` и текстом «`+1.5 1.543`»/«`Over 2.5 Sets 2.550`»/«`Имя 1.709`». Тип в id: 1=победа, 2=фора, 3=тотал. Две кнопки одной форы (+1.5 у обоих игроков) разводятся по кэфу.
